# 편집 기준서 — 신뢰성 검증 · 윤문 · 배치 · 디자인

모든 글은 이 기준을 통과해야 발행한다. 자동 점검은 `node scripts/check-claims.mjs <원고.md>`.

## 1. 신뢰성 검증 (5단계)

| 단계 | 할 일 | 산출물 | 자동화 |
|---|---|---|---|
| ① 주장 뽑기 | 원고의 모든 숫자·정책·기간·비율을 한 줄씩 적는다 | 원고 앞머리 `claims:` 출처 기록 | `check-claims`가 출처 기록에 없는 숫자를 찾아낸다 |
| ② 출처 등급 매기기 | 아래 등급표에서 가장 높은 등급의 출처를 찾는다 | 출처 기록의 URL | https 아닌 출처는 실패 |
| ③ 원문 재확인 | 출처 페이지를 **그날 직접 열어** 숫자를 본다. 정상가/회원가/할인가, VAT, 적용 모델·기간을 구분한다 | 출처 기록의 확인일 | 확인일 90일 경과 시 실패(`--max-age`) |
| ④ 표본 규칙 | 사용자 제보 수치는 표본 수와 함께. n<3 범위 미표시, n<5 중앙값 미표시 | 본문 표기 | 사이트 통계 모듈이 같은 규칙 적용 |
| ⑤ 하루 묵혀 재검 | 1인 운영이면 작성 다음 날 처음부터 다시 읽고 ③을 한 번 더 | 점검표 체크 | — |

**출처 등급**

| 등급 | 예 | 쓰는 법 |
|---|---|---|
| A 1차·공식 | 제조사 공식몰·서비스 요금 안내, 정부·소비자원 보도자료, 법령 | 그대로 인용 (확인일 필수) |
| B 공신력 2차 | 언론 보도(원 보도자료를 인용한 것), 학술 논문 | "보도 기준"으로 표기, 가능하면 A로 대체 |
| C 커뮤니티·블로그 | 카페·블로그 사례 | **수치 근거로 쓰지 않는다.** 링크·요약만, "개별 사례"로 표기 |
| D 생성형 AI 답변·근거 없는 요약 | AI 브리핑 수치, 출처 없는 표 | 사용 금지 |

**발행 후**: 분기마다 출처 기록 전체를 다시 열어 본다. 숫자가 바뀌면 표·한 줄 결론·업데이트 이력을 함께 고친다. 공식 요금 개정 예고(예: 삼성 에어컨 2027-01-01)는 캘린더에 재확인 일정을 넣는다.

## 2. 윤문 규칙

| 항목 | 규칙 | 예 |
|---|---|---|
| 첫 문장 | **질문에 대한 답 + 숫자 + 기준일**. 서론·인사말로 시작하지 않는다 | "LG전자 출장비는 평일 28,000원입니다(2026년 11월 공식 안내 기준)." |
| 제목 | 사람들이 실제로 묻는 문장에 맞춘다. 브랜드·모델·항목 + "얼마/비용" + 연·월 | "LG전자 출장비 얼마? 2026년 시간·계절별 정리" |
| 문장 | 한 문장 50자 안팎, 한 문단 2~3문장. 어미는 **블록 단위로 통일**한다(§5): 결론·표·고지는 합니다체, 설명·FAQ·확인 기록·CTA는 해요체. 한 문단 안에서는 섞지 않는다 | "LG전자 출장점검료는 평일 28,000원입니다." / "급하지 않다면 평일 18시 이전으로 예약하세요." |
| 숫자 | 천 단위 쉼표, 단위 붙여 쓰기(28,000원), 범위는 "~", 날짜는 2026-11-17 또는 2026년 11월 17일로 통일 | — |
| 단정과 추측 | 출처가 있으면 단정, 없으면 "확인하지 못했습니다" 또는 "표본이 부족합니다". "~것 같습니다" 금지 | — |
| 과장 | "최저가 보장·무조건·100%·업계 최저" 금지(표시광고 위험) | — |
| 업체 | 수리점·설치기사 **실명 평가 금지**. 제조사 공식 요금은 출처로 인용 가능 | — |
| 안전 등급 | 블로그는 한글 문장으로만 쓴다("주의: …", "여기서 멈추고 센터에 맡기세요"). 사이트 배지는 한글 + 영문 병기: "직접 점검 가능(Safe Check)", "주의(Caution)", "전문가만(Expert Only)", "직접 수리 금지(Do Not DIY)" | — |
| 질문형 소제목 | 독자가 검색할 질문을 소제목으로 쓴다(예: "출장비는 수리를 안 해도 내나요?") — 같은 사이트 안 인용과 가장 관련 있던 요인이 "질문과 맞는 제목·문단"이었다 [R12 G5] | — |

## 3. GEO·검색을 위한 원칙 (근거: `docs/research/R12`)

1. **AI 전용 장치보다 검색 기본기.** 구글은 AI 기능 최적화를 "여전히 SEO"로 본다(llms.txt·AI 전용 마크업 불필요). 색인, 스니펫 허용, 질문형 제목·첫 문단이 우선.
2. **가격·기준일·표본 수·출처를 본문 텍스트로.** 이미지 속 표는 검색·AI가 읽지 못할 수 있다. 표는 텍스트 표로.
3. **오래된 날짜를 방치하지 않는다.** 업데이트 이력과 확인일을 갱신한다.
4. **키워드 반복 금지.** 생성형 엔진에서 효과가 없거나 손해였다.
5. **채널 역할 분리**: 네이버 블로그는 AI 검색 크롤러(GPTBot·OAI-SearchBot·PerplexityBot·ClaudeBot 등)를 robots.txt로 차단한다(2026-11-18 확인). ChatGPT·Perplexity 인용은 **자체 사이트**가 맡는다 → 사이트 본문은 사전 렌더링 필요.
6. **같은 내용을 질문 변형마다 페이지로 복제하지 않는다**(구글 경고). 한 주제 한 페이지, 갱신으로 키운다.

## 4. 배치 — 고정 요소는 적게, 나머지는 글마다 다르게 (2026-11-18 개정)

첫 판(16블록 고정)으로 쓴 3편은 소제목·문장이 서로 겹쳐 템플릿으로 찍어낸 글처럼 읽혔다. 같은 템플릿 대량 발행은 구글·네이버가 모두 스팸으로 명시한다(R13 G3·N1). 점검 결과는 `docs/blog/AUDIT_HUMAN_SIGNALS.md`. 예시: `docs/blog/naver/01~03`.

**모든 글에 있어야 하는 것(고정)**

| 요소 | 규칙 |
|---|---|
| 첫 문단 | 라벨 없이 질문에 바로 답한다. 숫자 포함(검색 미리보기 문구가 된다). 공개 문장보다 앞에 둔다 |
| 공개 문장 | 광고·제휴 여부, 언제 무엇을 열어 확인했는지. 글마다 다른 문장으로 쓴다 |
| 만든 방법 | `만든 방법:` 한 줄을 **출처 목록 바로 아래**에 둔다(첫 화면에 두면 글 전체가 'AI 글'로 먼저 읽힌다는 독립 검토 지적, 출처와 함께 밝힐 때 신뢰 하락이 상쇄된다는 R13 S2). AI가 한 일, 사람이 원문·캡처를 다시 확인한 날짜, 방법론의 AI 사용 원칙 링크(§9-4) |
| 대표 이미지(썸네일) | 첫 이미지. 직접 찍은 사진이 있으면 사진 + 숫자, 없으면 썸네일 카드(질문 + 크게 쓴 검증 숫자 + 그 숫자가 보이는 원문 캡처 조각, `render-cards.mjs` thumb). 96px로 줄여도 숫자가 읽혀야 한다. 글자 캡처를 그대로 썸네일로 쓰지 않는다 |
| 증거 이미지 | 원문 캡처나 직접 찍은 사진 2장 이상, 숫자·문구가 나오는 문단 가까이에 |
| 표 아래 출처 줄 | 표마다 바로 아래에 "출처: ○○(확인일, 캡처 위치)" |
| 사례 | 검증 가능한 사례 1건 이상: 공적 사례·언론 보도·자사 제보·제조사 회신 인용(출처와 날짜를 문장에), 또는 편집자 직접 확인. 기준은 `CASES.md` |
| 행동 유도 | 제보 링크 1개(최대 2개) + 그 글에만 맞는 구체적 댓글 질문 |
| 출처 목록 · 쓴 사람 · 수정 이력 | 글 끝. 수정 이력에는 틀렸던 것과 고친 이유를 그대로 적는다 |

**글의 질문에 따라 고르는 것(가변)**: 질문형 소제목, 장단점 비교, "처음엔 이렇게 생각했는데" 단락, 직접 해 볼 수 있는 점검과 멈출 지점, 계산 예시, 구매 전 확인 사항. 순서와 개수를 글마다 다르게 둔다.

**쓰지 않는 것**: "한 줄 결론" 같은 라벨, 본문을 되풀이하는 FAQ 블록(G4), "편집자 확인 기록" 같은 시스템 라벨, 세 편에 같은 소제목, 같은 면책 두 줄 반복, 글마다 반복하는 "첫 원고는 틀렸다" 고백(수정 이력에만 둔다), 다른 글과 단어만 바꾼 문장(점검기가 유사도 0.5 이상을 실패 처리).

- **이미지**: 원문 캡처 2~3장 + 직접 촬영 0~2장 = 3~5장. 표는 이미지로 넣지 않고 에디터 표로 넣는다.
- **링크**: 출처 링크는 제한하지 않는다. 행동 유도 링크는 2개까지.
- **댓글**: 댓글 금액은 C등급이라 통계에 넣지 않는다. 다음 글의 질문 목록으로만 쓴다.
- **첫 글은 모바일 미리보기로 표·인용구 모양을 확인한다.** 스마트에디터 붙여넣기 서식 유지는 아직 확인하지 못했다.

## 5. 문체 — 격식체(합니다체)로 쓴다 (2026-11-18 개정, 사용자 검수)

해요체는 쓰지 않는다. 블로그 원고 전체를 합니다체로 쓰고, 행동 요청은 "~하십시오", "~해 주십시오", "~남겨 주시면 ~하겠습니다"로 쓴다. 점검기가 해요체로 끝나는 문장을 실패 처리한다(`informal_register`). 예외가 필요한 글만 front matter에 `register: polite`를 적는다.

**작업 보고 문장 금지**: "공식 페이지를 다시 열어 대조했고 그 화면을 캡처해 붙였어요"처럼 편집자나 AI가 한 일을 보고하는 문장은 챗봇이 사용자에게 보고하는 말투로 읽힌다. 같은 사실은 표 아래 출처 줄("출처: ○○(2026년 11월 18일 기준)")과 캡처 설명("…(2026년 11월 18일 화면)")으로 옮긴다. 점검기가 "대조했·캡처해 붙였·열어 확인·맞춰 봤·한 줄씩" 같은 표현을 잡는다(`work_report`). "만든 방법" 고지 줄만 예외다.

**광고·제휴 표기**: 본문과 다른 서식(인용구 블록)으로 한 줄만 쓴다. `> 광고·제휴 없이 작성한 글입니다.` 문장으로 늘어놓지 않는다.

윤문 기준은 `489156/koreanRewriting`(humanize-korean)의 quick-rules를 따른다. 특히 다음을 지킨다.
- 연결어미 뒤 쉼표를 쓰지 않는다(C-11). "~이라, ", "~했고, "를 쓰지 않는다.
- 같은 종결어미가 4문장 넘게 이어지지 않게 동사를 바꾼다(E-2).
- 결산형 "~라는 뜻입니다", "핵심은 ~"을 줄인다(I-3, D-8).
- 굵은 글씨와 대시를 남용하지 않는다(J-1, J-3).

측정은 그 저장소의 `scripts/prepare_monolith_input.py --genre blog`로 한다(위험 등급·route_hint).

금지: 반말, 인사 서론, 분량 채우기 문단(G4 Filler).

## 6. 디자인

**원고 속 이미지 = 원문 캡처 + 직접 찍은 사진** (`scripts/verify-sources.mjs --evidence`)
- 출처 기록 비고에 `캡처:이름`을 붙이면 그 문구가 있는 부분을 휴대폰 폭(430px, 2배 해상도)으로 찍는다. 빨간 테두리를 두르고 아래에 "원문 캡처 날짜 시각 · 주소"를 넣는다. `캡처:이름@다음이미지`는 문구 바로 뒤의 표·그래프 이미지를 찍는다.
- 캡처 전에 팝업 배경·고정 헤더 같은 덮개만 숨긴다. 페이지 내용은 건드리지 않는다.
- 캡처가 어둡거나 실패하면 한 번 더 실행한다. 소비자원 페이지가 가끔 그렇다.
- AI로 만든 고장·수리 이미지는 실물처럼 쓰지 않는다(R13 N1, G4).

**카드 이미지** (`scripts/render-cards.mjs`): 블로그 원고에는 썸네일(thumb) 1장만 넣는다. 요약·체크리스트 카드는 SNS 캐러셀 전용이다. 카드 숫자는 원고 출처 기록과 같아야 하고, `naver-export`가 대조한다. "광고·제휴 없음" 칩은 카드마다 `chip` 값으로 정하고, 제휴 링크가 있는 글의 카드에는 넣지 않는다.

**자체 사이트** (R11 §3-2. 다음 사이트 개편 때 적용)
- 본문 16px 이상, 줄간격 1.5 이상, 한 줄 한글 40자 이하, 대비 4.5:1 이상, 12px 미만 글자 금지.
- 표: 설명형은 2열, 숫자형은 4열까지.
- 요약 박스: 중앙값 / 중간 50% 구간 / 표본 n / 공임·부품 분리 / "포함 안 됨" / 확인일 / 방법론 버전.
- 안전 표시는 글자 라벨로 한다. 색만으로 구분하지 않는다(WCAG 1.4.1).

## 7. 바이라인과 검수

- 바이라인은 `쓴 사람:` 실명이나 활동명 + 한 줄 소개로 쓴다(G1 Who). "고장도감 편집자" 같은 익명 팀 라벨은 쓰지 않는다. 한 번 정하면 모든 글에 같은 문장을 쓴다.
- 1인 운영이면 작성자와 검수자를 나눈 척하지 않는다. 보완책은 두 가지다. 발행 전날 `verify-sources`로 다시 대조해 "만든 방법" 줄의 `마지막 대조일`을 갱신하고, 이미지 속 수치는 AI가 캡처를 읽어 확인한다. 사람이 다시 하는 것은 발행 승인이라는 판단이다.
- 외부 검수자(수리 기사 등)를 확보하면 "검수: 이름(자격)"을 추가한다. 실재하지 않는 인물이나 AI 가상 인물은 쓰지 않는다.

판정은 두 단계다. **실패**는 발행을 막고, **경고**(`WARN`)는 AI가 문맥을 보고 고칠지 정한다. `--strict`는 경고도 실패로 본다. `naver-export`는 경고만 있는 글은 내보낸다.

자동으로 처리하는 반복 작업: 일치한 출처 행의 확인일·`data_checked` 갱신(`--write`), 출처 기록에 없는 숫자의 원문 발췌 제안(`--suggest`), 캡처 재시도, 실행 기록(`evidence/<slug>/verify.json`), 검색어 수집·공백 분석·태그 후보(`demand-research`), 전체 글 현황(`blog-status`). 이미지 행 판독, 제안 행의 채택과 설명 작성, 경고 처리도 AI 몫이다. 사람 몫은 `[[판단]]`(바이라인·제휴·발행 승인)과 `[[현장]]`(통화·촬영·계정 키 발급)뿐이다(`CLAUDE.md` "사람 몫과 AI 몫").

출처 기록 한 줄 형식: `- 값 | 출처 | 확인일 | 비고 | 원문 인용 문구`. 비고가 `계산:`으로 시작하면 우리 계산값, `이미지:`로 시작하면 이미지 속 수치(캡처로 눈 확인)다.

## 9. 독자 신뢰 기준 — AI 티 · 검증 없는 내용 · 쉽게 만든 글 (근거: R13)

| # | 기준 | 근거 | 확인 방법 |
|---|---|---|---|
| 1 | 증거 이미지(원문 캡처·직접 사진) 1장 이상, 생성 이미지 금지 | G1 "evidence…such as photographs", G4 독창성, N1 | naver-export 이미지 수 + AI 캡처 판독 |
| 2 | 실제 사례 1건 이상(인용 또는 직접 확인) + 실패·수정 과정 공개 | N2 "직접 겪은 문제 해결 과정, 실패 경험", G1 | `사례:` 출처 줄 또는 `firsthand:`, 수정 이력 |
| 3 | 정책 문장까지 원문 인용 문구로 기록하고 발행 전날 실시간 대조 | N2 "공식 기관 자료 인용", "자주 변경되는 정보는 최신 상태로"; R13 K5(한국 AI 이용자의 원문 클릭 56%) | verify-sources |

법적 의무: 블로그에 AI 도구를 쓰는 운영자는 인공지능기본법상 "이용자"라 표시 의무 대상이 아니다. 다만 사이트에서 AI 견적·상담 기능을 제공하면 "인공지능이용사업자"로서 사전고지·표시 의무를 질 수 있다(R13 §2.3, 법률 자문 아님). 네이버 블로그의 'AI 활용' 표시는 선택 기능이다. 우리는 표시 여부와 관계없이 본문에 "만든 방법"을 쓴다.

## 10. 제휴 링크 (근거: R14, 상세: `docs/blog/AFFILIATE_PLAN.md`)

- 글마다 front matter에 `affiliate:`를 적는다. 쓰는 프로그램(`linkprice`·`shopping-connect`·`coupang`), 승인 전이면 `pending`, 이해충돌이거나 살 상품이 없으면 `none`.
- 링크 문법은 `[텍스트](aff:프로그램:발급받은 https 주소)`다. 주소는 고치지 않는다(UTM·단축·리다이렉트 금지).
- 고지는 본문 첫 줄에 단정형으로 쓴다(공정위: 제목 또는 첫 부분, "받을 수 있음" 금지). 쇼핑 커넥트는 필수 문구를 그대로 쓴다.
- 판정(수리 vs 교체)을 먼저 쓰고 링크를 고른다. 교체 상품을 링크하면 수리 경로도 같은 크기로 보여 준다. 호환 부품은 링크하지 않는다.

## 11. 독자·제목·가독성·검색어 (2026-11-18 사용자 검수 반영, 상세: `docs/blog/LESSONS.md`, `docs/blog/DEMAND_GEO.md`)

**상시 규칙(운영자 지시): 매번 발행 전에 수요자를 예상해 한 문장으로 정의한다.** front matter `demand:`에 "[누가] [어떤 상황에서] [무엇을 판단하려고] ['실제 검색어'를] 검색할 때 이 글을 읽습니다."를 맨 먼저 쓴다. 이 문장이 없거나, 평서문이 아니거나, 검색어가 빠지면 실패 처리한다(`no_demand_statement`). `naver-export`의 붙여넣기 페이지 맨 위에도 이 문장이 나온다. 발행 직전에 본문이 이 사람의 질문에 답하는지 다시 읽어 보라는 뜻이다. 새 원고는 `docs/blog/naver/_TEMPLATE.md`에서 시작한다.

수요자 문장과 함께 아래 다섯 칸을 쓴다. 비어 있으면 실패 처리한다(`no_demand_brief`).

| 칸 | 내용 |
|---|---|
| `reader` | 누가 읽는가. 품목·사용 기간·상황까지 |
| `need` | 무엇을 판단하려는가 |
| `urgency` | 얼마나 급한가, 이유 |
| `scale` | 그런 사람이 충분히 많다는 근거. 공식 페이지 조회수·리뷰 수·자동완성 질의 등 공개 지표 |
| `queries` | 실제 검색 질의. 구글 자동완성이나 네이버 키워드 도구에서 확인한 것 |

**제목**
- 독자의 질문과 구체적인 답(숫자)을 담거나 서술 문장으로 쓴다. 명사 나열("X, Y와 Z 기준 (날짜)")은 실패 처리한다(`title_style`).
- 핵심 검색어를 앞에 두고, 부품값만 말하면 "정품" 같은 한정어를 넣는다.
- 후보를 3~5개 만들어 독립 검토자에게 순위와 과장 여부를 받는다.

**품목 분류**
- 한 글은 한 품목만 다룬다. 제목의 "청소기"는 무선·로봇·유선 중 무엇인지 밝힌다(`ambiguous_category`).
- 범위 밖 자료는 별도 글로 옮기고, 본문 앞에 범위를 한 줄로 적는다.

**가독성**
- 한 줄에 1~2문장만 쓰고, 생각이 바뀌면 빈 줄을 둔다(`dense_paragraph`: 한 줄 3문장 이상 실패).
- 낯선 용어(소모성 부품, 유상, 사이클)는 처음 나올 때 풀어 쓴다.

**검색어 대응(GEO)**
- `queries`의 질의를 질문형 소제목과 첫 문장으로 답한다. 본문이 질의의 25%를 넘게 다루지 못하면 실패 처리한다(`query_coverage`).
- 태그는 실제 질의를 붙여 쓴 형태로 5~10개 단다. 네이버의 태그 반영 방식은 공개되지 않았으므로[unverified] 검색 매칭은 제목·소제목·첫 문장이 맡는다.
- 다루지 못한 질의(예: 배터리 버리기, 브랜드별 AS 비교)는 `DEMAND_GEO.md`에 "미반영"으로 적어 다음 글 후보로 남긴다.


## 12. 상황별 수리 가이드 (2026-11-19, 근거: `reports/셀프 집수리 공구 콘텐츠 전략.md`)
